# companion

Локальный персонаж для консоли: чат через Ollama, долгая память в SQLite,
сцены-кейсы с выбором реплик и датасет для будущего дообучения.

Это не замена SillyTavern. Это маленький стенд под конкретную задачу:
разыграть ситуацию по шагам, выбрать лучший вариант её ответа, поправить текст
и сохранить всю траекторию так, чтобы из неё потом можно было собрать SFT/DPO.

## Что внутри

- **Персонаж** — `persona.md`, правишь руками.
- **Кейс** — сцена: ситуация + необязательные поля (отношения, её цель, тон,
  ограничения).
- **Прогон** — одно прохождение кейса. Отдельная сессия, 5–20 ходов, в конце
  оценка 1–5 и заметка. Один кейс можно пройти много раз.
- **Варианты** — сначала 3 короткие заготовки, после выбора выбранная
  разворачивается в полную реплику с действиями в `*...*`.
- **Память** — последние сообщения дословно + сводка старых + факты.
- **Память модели** — `\+` загрузить, `\-` выгрузить, `\пс` посмотреть,
  что сейчас в RAM и до каких пор.
- **Скорость и этап** — во время генерации показывается текущий этап
  (подключение, загрузка модели/контекст, обработка контекста, генерация) и
  живая скорость. После ответа остаётся финальная строка
  `⏱ 10.0 ток/с · 10 токенов`. Для Ollama это точные
  `eval_count`/`eval_duration`, для OpenAI-совместимых — оценка с `~`.
- **Датасет** — каждый выбор, правка и оценка пишутся в `data/preferences.jsonl`;
  завершённый прогон целиком — в `data/runs/run_N.json`.
- **Бэкенды** — Ollama (нативно) или любой OpenAI-совместимый сервер.
- **Заглушка** — `--mock`, чтобы проверить интерфейс без модели.

## Быстрый старт

```bash
cd companion
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Ollama (Arch):

```bash
yay -S ollama
sudo systemctl enable --now ollama
ollama pull huihui_ai/qwen3-abliterated:8b-q4_K_M
```

Если ставишь без root, можно распаковать официальный tarball в `~/.local`
и запускать `ollama serve` от пользователя. В этом проекте так и сделано:

```bash
~/.local/ollama/bin/ollama list
systemctl --user status ollama
```

Юнит лежит в `~/.config/systemd/user/ollama.service`, модель —
в `~/.local/share/ollama/models`. Главное — чтобы `base_url` в `config.toml`
совпадал с портом.

Запуск:

```bash
./run.sh
```

Проверка без модели:

```bash
./run.sh --mock
```

## Модели

Для 16 ГБ RAM и CPU: 4B — быстрый вариант, 8B — качественнее, но примерно
вдвое медленнее. 8B Q4 занимает ~4.7 ГБ.

| Модель | Тег Ollama | Комментарий |
|---|---|---|
| Qwen3 8B Abliterated | `huihui_ai/qwen3-abliterated:8b-q4_K_M` | стоит по умолчанию; сняты отказы, взрослый контент |
| Qwen3 4B Instruct 2507 | `qwen3:4b-instruct-2507-q4_K_M` | официальная, безопасная, для SFW |
| Gemma 3 4B | `gemma3:4b` | мягче, хорошо держит персонажа |
| Qwen2.5 3B | `qwen2.5:3b-instruct` | быстрее, слабее в сложных сценах |
| Llama 3.2 3B | `llama3.2:3b` | русский заметно слабее |

8B на этом CPU даёт примерно 5–6 ток/с. Для кейсов это рабочий вариант,
но первый ответ после загрузки может занять минуту: 8B долго считает
системный промпт. Дальше prompt cache ускоряет ходы.

8B-тег Qwen3 по умолчанию «думающий» и сыпет `<think>`. В `config.toml`
включён `no_think = true`, а приложение вырезает теги из ответа.

### Потоки

На Ryzen 5 5650U Ollama автоматически берёт 6 физических ядер. Принудительные
12 логических потоков на 8B дали **4.56 ток/с против 6.15**, на 4B —
**5.0 против 8.7**. Поэтому `num_thread = 0` (авто) — правильный выбор.
SMT для LLM здесь только мешает. На сервере с 20 потоками ставь 8–10,
чтобы не душить Minecraft.

### Swap

Сейчас swap — это `/dev/zram0` на 4 ГБ, то есть сжатая RAM, а не диск.
Для 8B обычно хватает, но для 12B в ветке `main` этого мало. Добавить
нормальный 16 ГБ swapfile:

```bash
sudo bash tools/add_swap.sh
swapon --show
free -h
```

Скрипт создаёт `/swapfile`, включает его и прописывает в `/etc/fstab`.
zram остаётся с приоритетом 100, файл — с приоритетом 10: сначала
используется сжатая RAM, потом диск.

## Взрослый контент

По умолчанию стоит `huihui_ai/qwen3-abliterated:8b-q4_K_M`:
у неё снято «направление отказа», поэтому она спокойнее относится к взрослым
сценам. Но:

- персонажи только взрослые, всё только по взаимному согласию;
- у персонажа остаются границы: она может отказаться или попросить подождать;
- после abliteration качество может просесть — повторы и странные ответы
  случаются чаще, чем у официальной модели;
- если нужен SFW-режим, поменяй `model` в `config.toml` обратно на
  `qwen3:4b-instruct-2507-q4_K_M`, поставь `[content] adult = false`
  и убери раздел «Близость» из `persona.md`.

`\кп` получает полную карточку персонажа и взрослый блок. Если идея про секс,
промпт требует начинать ситуацию уже во время близости, а не с прелюдии.
Если 4B всё равно смягчает сцену — это ограничение модели, не промпта.

## Кейсы

Быстрый набор:

```text
\к
кейс › она нашла мой старый профиль и ревнует
кейс › первое свидание, оба нервничают
кейс › она заболела, а я опять залип в сервер
(пустая строка)
✓ добавлено 3, всего 12
```

Одна строка:

```text
\к она нашла мой старый профиль и ревнует
✓ кейс #12
```

Если не хочется придумывать условия самому:

```text
\кп ревность
```

Модель предложит ситуацию, отношения, цели, тон и запреты. Дальше:

- `Y` — сохранить
- `e` — поправить поля
- `r` — сгенерировать заново
- `n` — отмена

Один такой запрос на 4B занимает примерно 30–60 секунд. Это один вызов
модели, не цикл.

Дополнить поля (пустой ввод — оставить как есть):

```text
\к+ 12
ситуация [она нашла мой старый профиль и ревнует] ›
отношения [] › встречаемся три месяца
её цель [] › получить объяснение, а не оправдание
тон [] › серьёзный, с колкостями
нельзя [] › мириться в первые три хода
кто начинает (her/me) [her] ›
теги [] ›
```

Список:

```text
\ксы
```

Прогон:

```text
\к 12
── кейс #12 · прогон #3 ──
Алиса: «ты серьёзно думал, что я не найду?»

1) ...
2) ...
3) ...
1/2/3 · e править · r заново · s пропустить
```

Дальше:

```text
ты › я не прятал, просто не удалял. разница же
(3 варианта её ответа)
2
```

Завершение:

```text
\ч
оценка 1–5 › 4
заметка › слишком быстрое примирение
✓ прогон #3 закрыт · 12 ходов · 4/5
```

Если закрыть терминал, прогон останется активным. При следующем запуске
`\п` вернёт в него.

`\пд` — три подсказки для твоей реплики. Они только показываются, в датасет
не сохраняются.

## Варианты и действия

В режиме `\м 3` (и всегда в кейсах) модель сначала выдаёт не полные ответы,
а короткие заготовки:

```text
короткие заготовки:
  1. явился, блин
  2. ты вообще думал?
  3. кофе будешь?
выбор [1-3, e=править, r=заново, s=пропустить] ›
```

После выбора она разворачивает заготовку в живую реплику на 2–3 предложения:

```text
Алиса › *отводит взгляд* явился, блин. *садится обратно* я уже думала, ты не придёшь.
⏱ 9.3 ток/с · 24 токена
```

Если разворот получился пустым, приложение предлагает повторить или отменить
ход. При отмене удаляется только текущая неудачная реплика пользователя, а не
предыдущая история.

Действия и мимика оформляются звёздочками: `*улыбается*`, `*отводит взгляд*`,
`*садится рядом*`. Одно–два действия на реплику, не больше. Если действие
не нужно, персонаж говорит только словами.

В `config.toml`:

```toml
[chat]
variant_mode = "short"   # сначала заготовки, потом разворот
# variant_mode = "full"  # сразу полные варианты, полезно для DPO
short_max_tokens = 80
```

## Команды

| Команда | Что делает |
|---|---|
| `\к текст` | добавить кейс |
| `\к` | режим набора: строка = кейс, пустая — выход |
| `\к 12` | начать прогон кейса |
| `\к+ 12` | дополнить поля кейса |
| `\кп [идея]` | модель предложит условия кейса |
| `\ксы` | список кейсов |
| `\ч` | завершить прогон: оценка 1–5 + заметка |
| `\п` | продолжить незакрытый прогон |
| `\пд` | 3 подсказки для твоей реплики |
| `\м` / `\мфк` | число вариантов |
| `\г` | удалить последний обмен |
| `\у` | править последнюю реплику |
| `\д` | лайк последней реплике |
| `\+` | загрузить модель в память |
| `\-` | выгрузить модель |
| `\пс` | что загружено, сколько ест, до каких пор |
| `\р` | помощь |
| `\й` | выход |
| `\ые` | статистика |

Длинные варианты: `/case`, `/cases`, `/finish`, `/resume`, `/hint`, `/abandon`,
`/load`, `/unload`, `/loaded`.
Экспорт — `/export md` или `/export jsonl`.

Удаление кейса по умолчанию **архивирует** его: `/case del 12` убирает кейс из
списка, но все прогоны остаются в базе. Показать архив — `/cases all`.
Жёсткое удаление вместе с прогонами — `/case purge 12`, только после
подтверждения.

Работают и обычные команды:

| Команда | Что делает |
|---|---|
| `/variants N` | N вариантов в обычном чате (0 — поток) |
| `/again` | перегенерировать последний ответ |
| `/undo` | удалить последний обмен |
| `/edit` | отредактировать последний ответ |
| `/like`, `/dislike` | оценка последнего ответа |
| `/remember текст` | добавить факт в память |
| `/facts`, `/forget ID` | посмотреть и убрать факты |
| `/compact` | сжать старые сообщения в сводку |
| `/persona`, `/persona edit` | показать и отредактировать карточку |
| `/new`, `/sessions`, `/switch ID` | сессии |
| `/model имя`, `/temp X` | модель и температура |
| `/export [md\|jsonl]` | выгрузить диалог |
| `/stats` | статистика |
| `/quit` | выход |

## Память модели

По умолчанию модель держится в RAM бессрочно (`keep_alive = -1`): первый токен
быстрый, но занято около 3.6 ГБ.

```text
\+    загрузить заранее
\-    выгрузить
\пс   что загружено, сколько ест и до каких пор
```

После `\-` следующее сообщение загрузит модель заново: ~7 секунд на загрузку
плюс пересчёт системного промпта. Для экономии RAM это нормально, для частого
чата — заметно.

В `config.toml`:

```toml
[llm]
keep_alive = -1   # -1 — всегда, "30m" — полчаса простоя, 0 — сразу после ответа
```

`/load` всегда загружает надолго, `/unload` выгружает сразу — независимо от
`keep_alive`. Если `keep_alive = 0`, обычный чат будет выгружать модель после
каждого ответа; так лучше не делать на CPU.

## Как устроена память

1. Все сообщения лежат в SQLite.
2. В промпт попадают последние `history_messages` (40) и все факты.
3. Когда сообщений без сводки становится больше `summarize_after` (36),
   модели отправляются **предыдущая сводка + новые сообщения**. Она возвращает
   обновлённую сводку, а не новую с нуля, поэтому старые события не теряются.
4. Сводка и новые факты сохраняются; старые сообщения остаются в базе, но в
   контекст больше не попадают.
5. `/compact` запускает сжатие вручную.

В кейсах автосжатие не запускается: прогон обычно короче 40 сообщений, а
терять детали сцены не хочется.

## Датасет

`data/preferences.jsonl` — по одной JSON-записи на строку. Для кейсов там есть
`case_id`, `run_id` и `kind` (`case_opening`, `case_turn`, `case_retry`,
`choice`, `edit`, `rating`, `run_finish`).

Из записей `choice` получаются пары `chosen` / `rejected` для DPO, из `final`
и `rating=1` — примеры для SFT. Скрытая стартовая инструкция в контекст
датасета не попадает. У каждого кандидата в логе есть `stats`: число токенов,
время и токены в секунду — пригодится, чтобы отбирать не только удачные,
но и не слишком медленные ответы.

В режиме `short` запись выглядит иначе: `short_candidates` (что предлагалось),
`chosen_short`, `short_edited` и `final` (развёрнутая реплика). Для SFT
используется `final`; для DPO в этом режиме нет полных отклонённых ответов,
поэтому пары `chosen`/`rejected` лучше собирать с `variant_mode = "full"`.

`data/runs/run_N.json` — завершённый прогон целиком:

```json
{
  "run_id": 3,
  "case_id": 12,
  "case": {"situation": "...", "tone": "..."},
  "rating": 4,
  "notes": "...",
  "messages": [
    {"role": "assistant", "content": "..."},
    {"role": "user", "content": "..."}
  ]
}
```

Нужно 300–1000 разнообразных ситуаций: быт, ссоры, скука, планы, близость,
несогласие. Если писать только флирт, модель научится только флиртовать.

## Перенос на сервер

На сервере (Xeon E5-2680 v2, 24 ГБ) Ollama живёт постоянно, ноут — клиент.

`/etc/systemd/system/ollama.service`:

```ini
[Unit]
Description=Ollama
After=network-online.target

[Service]
ExecStart=/usr/local/bin/ollama serve
Environment="OLLAMA_HOST=0.0.0.0:11434"
Environment="OLLAMA_MODELS=/srv/ollama/models"
Environment="OLLAMA_NUM_PARALLEL=1"
Environment="OLLAMA_MAX_LOADED_MODELS=1"
Environment="OLLAMA_KEEP_ALIVE=-1"
Restart=always
User=ollama

[Install]
WantedBy=multi-user.target
```

На ноуте в `config.toml`:

```toml
[llm]
base_url = "http://IP-СЕРВЕРА:11434"
num_thread = 8
```

`num_thread = 8`, чтобы Ollama не съела все 20 потоков и не душила Minecraft.
Если Minecraft тормозит, прижми Ollama к ядрам через `CPUAffinity=0-7`,
а Minecraft — к остальным.

E5-2680 v2 — Ivy Bridge, без AVX2. Ollama сама подберёт CPU-раннер. Если
собираешь `llama.cpp` руками, не включай AVX2.

Порт 11434 не выставляй в интернет: у Ollama нет авторизации. Только LAN
или Tailscale.

## Дообучение

- 1.5B LoRA (bf16/fp32) на 500–1000 примеров — ночь-две на Xeon.
- 4B LoRA — несколько суток, лучше арендовать GPU на 2–3 часа.
- 7–8B — только GPU.
- DPO — после SFT и только на GPU.

Порядок: накопить датасет, один прогон SFT, затем сравнить старую и новую
версию на фиксированном наборе из 30–50 ситуаций. Без слепого сравнения новая
модель всегда будет казаться лучше.

## Ограничения

- Память — это сводка + факты, а не настоящее понимание. Она ошибается.
- 4B на CPU путает факты и повторяется. Это лечится памятью, отбором и
  дообучением, но не до конца.
- В кейсе варианты генерируются целиком, без стриминга: на CPU это заметно.
- Конфиг не сохраняется из интерфейса: `/model`, `/temp`, `/variants` живут
  до выхода. Постоянные значения — в `config.toml`.
- Ветвления по сюжету нет: сцена линейная, меняются только реплики.
